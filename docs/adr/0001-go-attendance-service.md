# ADR 0001: Перенос авторизации и отметки посещаемости на Go-сервис с базой студентов

## Статус

**Принято** (2026-11-08).

Переход на целевую архитектуру идёт в два шага на двух ветках:

1. `docs/refactor-architecture` — настоящий ADR и обновление документации под целевой
   контракт (текущая ветка). До слияния с кодом документация описывает целевое
   состояние, а не текущее.
2. `service/refactor` — реализация: Go-сервис (`server/`), PostgreSQL-схема,
   Android-клиент сервиса, удаление WebView-потока.

## Контекст

Сейчас вся работа с LMS выполняется на устройстве:

- Активный путь — **WebView-автоматизация** (`BrowserScreen()`): для каждого аккаунта
  последовательно загружаются страницы Moodle, JS-инъекции заполняют формы. На аккаунт
  уходит 8–20 секунд, обработка строго последовательная, успех определяется по
  «магической» константе `view.php?id=122864&success=true`, после каждого успеха —
  пауза 1,5 с.
- Аккаунты хранятся **локально на устройстве** (`AccountManager` →
  `EncryptedSharedPreferences`, ключ `accounts_list`); миграций схемы нет.
- `MoodleClient.kt` — вспомогательный HTTP-клиент, к UI не подключён; в нём же
  латентный баг — хардкод `status=1` вместо выбора статуса по подписи.

Ограничения текущего решения:

- последовательная обработка + полный рендеринг WebView — минуты на группу студентов;
- «магическая» навигация по `success=true` и хардкод `status=1` хрупки;
- список аккаунтов привязан к одному телефону — нет общего хранилища, нельзя
  централизованно отметить группу студентов.

Ключевой технический факт: LMS (`lms.uni-dubna.ru`, Moodle) — server-rendered
PHP-приложение **без антибот-защит**. Логин и отметка — обычные HTML-формы с
серверными CSRF-токенами (`logintoken`, `sesskey`), работающими без JavaScript.
Это подтверждено существованием `MoodleClient.kt`, реализующего весь сценарий
чистыми HTTP-запросами.

## Решение

1. **Отдельный Go-сервис** (каталог `server/` в этом репозитории) берёт на себя весь
   сетевой сценарий: логин в Moodle, отметку посещаемости, параллельную обработку
   списка студентов. На каждого студента — собственный `http.Client` с изолированным
   cookie jar; обработка идёт пулом воркеров с ограничением конкурентности
   (по умолчанию 5, настраивается через env).
2. **PostgreSQL** — единственное хранилище аккаунтов: таблица `students`
   (`first_name`, `last_name`, `study_group`, `lms_login` UNIQUE, `lms_password`,
   `is_selected`). Локальное хранилище аккаунтов на устройстве удаляется.
3. **API сервиса** (контракт — `docs/openapi.yaml`):
   - CRUD `/api/students` — пароли в ответах никогда не возвращаются;
   - `POST /api/mark` — запуск отметки по `qrUrl` и списку `studentIds`
     (пустой список = все с `is_selected = true`); результаты — поток **SSE**
     (`text/event-stream`): событие `result` по мере готовности каждого студента,
     финальное `done`, heartbeat-комментарии `: ping`;
   - `GET /health` — проверка HTTP и доступности БД;
   - авторизация — `Authorization: Bearer <token>` на всех ручках, кроме `/health`.
4. **Android-приложение** становится клиентом сервиса: сканер QR сохраняется,
   `AccountsScreen` работает через CRUD-API, новый `MarkingScreen` отправляет
   `POST /api/mark` и читает SSE-поток. Локально остаётся только конфигурация
   сервиса (URL + токен) в `EncryptedSharedPreferences` под отдельным ключом.
   Удаляются: WebView-ветка (`BrowserScreen`, JS-инъекции, `parseQrPassword()`),
   `MoodleClient.kt`, `AccountManager` и ключ `accounts_list`.
5. **Механика Moodle переносится с исправлениями**:
   - статус «присутствовал» выбирается парсингом радиокнопок по подписи
     («present», «присутств», «был/была/были», «явился/явилась», «уважительн»,
     иначе первая); хардкод `status=1` не переносится;
   - «уже была отмечена» / «already been marked» → статус `already` (считается успехом);
   - константа `view.php?id=122864&success=true` не переносится — она нужна была
     только для навигации WebView;
   - сервис сам разбирает QR-ссылку: `sessid` обязателен, пароль — `qrpass` |
     `password` | `studentpassword` (приоритет по убыванию); ссылки с host, отличным
     от `lms.uni-dubna.ru`, отклоняются;
   - базовый URL LMS остаётся захардкоженным: `https://lms.uni-dubna.ru`.

## Последствия

**Положительные:**

- Отметка N студентов занимает секунды вместо минут: параллельные горутины,
  ~4 HTTP-запроса на студента вместо загрузки и рендеринга страниц в WebView.
- Единое хранилище аккаунтов: управление с любого устройства, отметка всей группы.
- Пароли перестают передаваться на телефон и храниться на нём; приложение хранит
  только адрес сервиса и токен.
- Уходят хрупкие элементы WebView-потока: `success=true`-навигация, паузы,
  зависимость от JS-инъекций.

**Отрицательные / риски (приняты осознанно):**

- `lms_password` хранится в БД **открытым текстом**: дамп БД равносилен утечке всех
  паролей LMS. Компенсации: сервис закрыт bearer-токеном, доступ к БД ограничивается
  на уровне хоста. Обратимое шифрование на стороне приложения (AES-GCM, ключ из env)
  — возможное будущее улучшение (потребует отдельного ADR).
- Пароль студента передаётся по сети телефон → сервис только при создании/изменении
  записи; для защиты трафика рекомендуется LAN или TLS.
- Появляется зависимость от доступности сервиса и БД: без сервиса приложение отметку
  выполнить не может (WebView-фолбэк удалён).
- Сохранённые локально аккаунты **не переносятся** (миграций нет): после обновления
  студенты вносятся в БД заново.
- Если университет включит CAPTCHA или SSO (CAS/OAuth) на логине, чистый HTTP-сценарий
  перестанет работать — потребуется новый ADR (например, возврат браузерного фолбэка).
- Десятки одновременных логинов с одного IP заметны администратору LMS; конкурентность
  ограничена пулом воркеров и настраивается env-переменной.
